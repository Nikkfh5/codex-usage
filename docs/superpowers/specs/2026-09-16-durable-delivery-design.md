# Надёжная доставка расхода Codex

Статус: решение согласовано пользователем; реализация проверяется перед выпуском. Текущее состояние и команды — в README.md.

## Задача и проверенные факты

Устранить повторяющиеся потери при обрывах сети, смене прокси, остановке отправителя
и временной недоступности сервера на всех подключённых машинах.
Разовая дозагрузка исторических пропусков не является исправлением доставки.

Сейчас Codex напрямую отправляет OTLP на Aeza. Получатель считает принятые события
правильно, но не может восстановить пакеты, потерянные до его получения.
В локальных JSONL уже есть `token_usage_record` с `response_id` и отдельными
счётчиками. На ASUS проверены 456 записей из шести сессий 16 сентября:
обязательные поля и контекст модели присутствуют, total = input + output.
Это проверка версии CLI 0.153.4; совместимость других клиентов проверяется при установке.

## Варианты

| Вариант | Что решает | Ограничение |
| --- | --- | --- |
| Отправитель из существующих журналов, Aeza сохраняется | Повторная доставка после обрывов и остановки отправителя; устойчивый ID ответа | Нужен небольшой фоновый процесс на каждой машине и явный переход источника учёта |
| Локальный OpenTelemetry Collector с дисковой очередью | Сохраняет уже полученные OTLP-пакеты при недоступном сервере | Не восстанавливает то, что потерялось между Codex и выключенным Collector; старый OTLP не имеет response_id |
| Vercel и внешняя база | Меняет хостинг и развёртывание | Сам по себе не исправляет потерю пакетов на клиенте; нужна миграция Python HTTP-сервера и SQLite |

Рекомендация: первый вариант. Код хранить в приватном Git-репозитории;
приёмник и существующий интерфейс пока оставить на Aeza. Миграция хостинга не должна
задерживать исправление доставки и не является условием её надёжности.

## Поток данных

`JSONL Codex → локальный журнал счётчиков в SQLite → HTTPS → SQLite сервера → сайт`.

Один небольшой отправитель на машину, Python со стандартной библиотекой.
Автозапуск и восстановление процесса средствами ОС: Task Scheduler на Windows,
launchd на macOS, systemd на Linux. Отдельный CODEX_HOME подключается явно.

1. Читать только завершённые строки журналов. Сохранять уникальный ответ и позицию
   чтения одной транзакцией; неполную последнюю строку дочитывать при следующем обходе.
2. Хранить только разрешённые идентификаторы, дату, модель и счётчики. Тексты диалогов,
   результаты инструментов, email и ключи в очередь и на сервер не копировать.
3. Не суммировать накопительные `thread_token_usage`, `turn_token_usage` и дублирующие
   `token_count`. При неподдерживаемом формате показывать ошибку совместимости.
4. Отправлять небольшие пакеты. Ошибка сети, HTTP 429/5xx и потеря ответа сервера
   оставляют записи неподтверждёнными; повторять с задержкой без истечения срока.
5. Сервер подтверждает конкретные ID только после транзакционного сохранения.
   Повтор одного ID с теми же данными не меняет сумму; другой payload с тем же ID
   вызывает конфликт, а не молчаливую перезапись. Один response_id нельзя повторно
   посчитать под другой машиной: конфликт происхождения требует разбора.
6. Подтверждённые нормализованные записи сохранять локально для повторной сверки
   и восстановления после отката серверной базы. Не удалять их по тайм-ауту.
7. Отправитель использует собственный явно выбранный маршрут HTTPS. По умолчанию —
   прямое соединение с DNS-адресом; старые переменные прокси процесса Codex не наследует.
   Если машине нужен прокси, задаётся явный адрес. Сбой любого маршрута не очищает очередь.

## Совместимость и переход

Идентификатор ответа — `response_id`, имя машины берётся из подтверждённой локальной
настройки. Перенесённые журналы не получают автоматически имя нынешнего компьютера.
Установщик фиксирует текущую границу чтения существующих файлов и отдельно проверяет
новые ответы; загрузка старой истории проходит через сверку происхождения.

Единица перехода — целая сессия `session_meta.id` / `thread_id`. API `session_id`
подагента может указывать на родителя; сопоставление с реальным OTLP подтвердило,
что для идентичности нужен thread ID. После полного чтения и подтверждения всех
ответов сессия активируется: аналитика использует только журнал, оригинальные OTLP
сохраняются. До активации журнал не прибавляется к OTLP. Исторические суммы могут
измениться из-за различного состава событий; похожие счётчики не склеиваются.
Сессии до установки требуют явного подключения; история другой машины или другого
отправителя блокирует переход. Неполная/неподдерживаемая история не активируется.

До переключения конкретного App/CLI/IDE надо доказать, что его новые ответы появляются
в доступном журнале. Непроверенный клиент остаётся помеченным как непроверенный.
Нет необходимости закрывать активные Codex-процессы для чтения уже записанных журналов.

## Наблюдаемость и восстановление

В существующей карточке машины показывать время последней сверки, состояние
синхронизации и последний известный размер очереди. При потере связи последнее
известное значение не выдавать за текущее. Ошибка чтения/формата или заполнение диска
должны быть видимыми; отсутствие новых токенов не является доказательством исправности.

Периодическая сверка ID/сумм за закрытые интервалы проверяет, что подтверждённые ранее
ответы остались на сервере; расхождения автоматически восстанавливаются из локального
журнала. Сервер подтверждает прогресс сверки только после её завершения.

Развёртывание сервера — новый проверенный выпуск с резервной копией SQLite и откатом.
На каждую машину нужен один запуск установщика. Готовый установщик без реальной
проверки на машине не считается её подключением. Адреса других машин пока не предоставлены.

## Приёмочные проверки

- Сервер недоступен: новые ответы остаются на диске; после восстановления все доставлены.
- Отправитель остановлен во время работы Codex: после запуска дочитывает пропущенные строки.
- Отправитель аварийно завершается после записи очереди и после серверного commit,
  но до локального подтверждения: после запуска потерь и удвоений нет.
- Повтор пакета, параллельные повторы и одинаковый ID с другим payload проверяются отдельно.
- HTTP 401/429/500, неверный прокси, неполная JSONL-строка, перенос/ротация файлов,
  неподдерживаемая версия и недоступный диск не превращаются в успешную синхронизацию.
- Откат серверной базы: периодическая сверка восстанавливает отсутствующие подтверждённые ID.
- На границе перехода OTLP/журнал один ответ учитывается один раз; исходные записи сохранены.
- В локальной очереди и серверной базе нет sentinel-текстов из prompt/tool output.
- Синтетические сетевые сбои проверяются на отдельном тестовом сервере; затем реальные
  новые ответы каждой доступной машины сверяются по ID и счётчикам с API и CSV.

Гарантия относится к ответам, которые Codex записал в локальный журнал, при сохранном
локальном хранилище. Нельзя обещать восстановление ответа, который сам Codex не записал,
или переживание уничтожения всех копий данных. Это не измерение списания подписки.
